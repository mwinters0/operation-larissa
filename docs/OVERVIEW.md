# Overview: what is built on top of the port

Operation Larissa is two things at once. It is a **faithful port** of *Operation Neptune* (The Learning Company, 1998, `ONWIN32.EXE`)
to Godot 4.7, checked against the original's bytes; and it is a **model project for teaching game programming**, whose code is
written to be read and whose content anyone can change, extend and share. This page is the tour of the systems that make the
second possible without giving up the first. Each section says what the system is, why it exists, and where to read more.

For the reader in a hurry: [`README.md`](../README.md) has the documents by audience; agents read [`CODEMAP.md`](CODEMAP.md).

## The model: three layers

Everything in the project belongs to one of three layers, and the layer says who may change it.

| Layer | What it is | Who changes it |
| --- | --- | --- |
| **Rules** | the 12.17 Hz `GameClock` tick, integer 640 x 400 window coordinates, the creature interpreter `FoeVM`, tile-scan walls, hit rectangles, oxygen, ink, pieces, how a problem is judged | their code: nobody; their values (speeds, limits, waits): a pack's `rules/tuning.json` ([`engine/ARCHITECTURE.md`](engine/ARCHITECTURE.md), "Rule values are data"); a campaign's declared mods add behaviour at three named hooks, as plain data the game checks (same file, "Rule hooks") |
| **Content** | sectors, screens, creature scripts, triggers, problems, texts, sounds, pictures, campaigns, the lengths of waits | the editors; packs; student campaigns |
| **Presentation** | everything that reads rule state and draws or plays it | skins; the original look is the first skin |

The authoritative port is rules plus content traced to the original bytes; the level editor is content tooling; a graphical
overhaul is presentation; a student campaign is content (plus, optionally, a skin). None of these needs a second codebase.

**Where the fork is.** A change to how an existing rule works ends what this codebase does: fractional coordinates or engine
physics instead of the tile scan, another tick rate, scrolling or larger screens, creatures whose behaviour lives in scenes instead
of `FoeVM` scripts, 3D gameplay. After any of these the original sectors are no longer guaranteed to play as designed and the
fidelity tests stop meaning anything; such a remake belongs in a separate project that takes this one as its specification and
content source. High resolution is *not* a fork: the rules keep 640 x 400 as their coordinates, and `stretch/mode="canvas_items"`
draws 4x art at scale 0.25 sharply, which is a skin's business.

The creator-facing version of this model, with what each layer means for your own content, is
[`create/CONTENT.md`](create/CONTENT.md), section 1.

## Principles every system keeps

- **Fidelity stays checkable.** Tests built from hashes of the original's bytes guard the original sectors and tables; every kept
  difference is either listed in a test's `DELIBERATE_*_CHANGES` constant or is a "Deliberate deviation" (code comment, test,
  `port/DESIGN.md`).
- **Provenance is never lost.** Everything derived from the original is regenerated by the importer from the user's own copy and is
  traced to a file, resource id and offset on the CD; hand-made layers (names, comments, durations) are stored apart from it.
- **Fixtures commit hashes, not bytes.** A fixture holds provenance and one SHA-256 per whole record (a hash of a one-byte field
  could be reversed by trying every value). The bytes are written by the importer to a git-ignored folder.
- **Skins never change rules or timing,** and a test proves it for every skin that exists.
- **Tools stay ordinary Godot** (plugins, main screens, tool scenes, the Inspector), so they remain teaching material.

## The port: rules as plain objects, scenes as views

The game is a set of scenes (opening, sign-in, the mission, the problem screens, the closings), but the rules of a sector are a
plain object, `SimWorld`, that runs one `tick(input)` in the original's order and reports what happened as named events. What
happens next in a mission (dock, lock, next sector, game over, finale) is another plain object, `GameFlow`. Scenes only show
them: a `SectorPresenter` draws a `SimWorld`, and the `Game` scene is the view of a `GameFlow`. Every length that holds up play is
counted by the rules or read from data, never taken from an animation. Tests read the rules' source to keep them free of nodes,
and play whole sectors with no scene at all.

Read: [`engine/ARCHITECTURE.md`](engine/ARCHITECTURE.md). The original game's behaviour, which the rules implement, is
[`port/DESIGN.md`](port/DESIGN.md); which Godot concept each file teaches is [`engine/TEACHING.md`](engine/TEACHING.md).

## Provenance: the legacy pack, the importer and the fidelity tests

The repository holds none of the original game. The importer (`tools/import/import_all.py`) builds it from the user's own
`NEPTUNE.ISO`, after checking every game file against the hashes of the reference release, into **the legacy pack**
(`godot/packs/legacy`, git-ignored). It is deterministic: the same ISO gives the same bytes and the same Godot uids. It writes an
asset manifest that says where every file came from, and the original bytes behind the committed hash fixtures. Each kind of
original record (sector headers, creature records and scripts, screens, sprite metadata, trigger table, zones, problem tables)
has an encoder, a fidelity test and a reset tool that puts it back.

Read: building and playing it, [`play/LEGACY.md`](play/LEGACY.md); fixtures, encoders, reset tools and the fidelity rules,
[`port/FIDELITY.md`](port/FIDELITY.md); the formats of the game's files, [`port/ASSET_FORMATS.md`](port/ASSET_FORMATS.md).

## Names

The original knows things by number (sound 22, creature picture 40, flag 3). A hand-made registry, `godot/names/original.json`,
gives every number a friendly name, and everything above the rules uses names: creature scripts (`Play_Sound begin`), code and
data, skins, packs and asset file names. Unnamed numbers get a fallback name (`sfx_28`), and a rename tool changes a name
everywhere at once.

Read: [`create/NAMES.md`](create/NAMES.md).

## The level editor

The original designers' tool, rebuilt inside the Godot editor and limited to the original's formats: the **screen editor** (one
screen as a scene: tiles, decorations, triggers, pieces, creatures; a playtest of that screen), the **sector inspector** (the
sector's header, pieces and creatures, with undo), the **Foe Script editor** (creature scripts as text, with names, completion, a
sandbox run and a debugger that marks the paused line), the **sector overview** (all twelve screens on one map, reachability,
creature paths, check findings), **Check sector** (what changed from the original, and whether a sector is playable) and **New
sector** (from a template or a copy).

Read: the manuals [`create/SCREEN_EDITOR.md`](create/SCREEN_EDITOR.md), [`create/SECTOR_INSPECTOR.md`](create/SECTOR_INSPECTOR.md),
[`create/FOE_SCRIPTING.md`](create/FOE_SCRIPTING.md); how the tools are built, [`engine/EDITORS.md`](engine/EDITORS.md).

## Campaigns

A campaign is one whole game as data (`Campaign`): the ordered sectors, the finales, the starting levels, the canister log, the
supply messages and the closing. Voyager and Expert are two campaigns of the legacy pack; a student campaign is a third file
beside them, with words of its own and a generic finale. Saves are keyed by campaign.

Read: [`create/CONTENT.md`](create/CONTENT.md), section 3; the tutorial [`create/MAKING_CONTENT.md`](create/MAKING_CONTENT.md).

## Skins

A skin (`GameSkin`) is the presentation layer as data: pictures by name, high-resolution art, fonts, shaders, render settings and
even a whole presenter scene, with everything it does not map falling back to the original. A presenter sees the rules only
through `SimView` (copies of the state and 28 events), and every skin in `godot/skins/` is played against the original by the
tests and must give the same trace. One skin besides the original is in the project: `creatures` (an animation-tree fish and a 3D puffer;
models and animation trees need real nodes, so only a project skin can do that). `modern` (a water shader and another font, no code) is the
example of a skin pack, `examples/packs/modern/`, played by the same tests.

A skin from a stranger is a mod pack: a sandboxed script that is given the state as plain data and returns what to draw, so it can change nothing but the picture; it is chosen like any other skin and played by the same tests.
A mod pack can also add gameplay: a campaign names the mods it uses, and only a run of that campaign asks them, at three points (the judging of the answers of a problem type the mod added, a creature instruction, a sub ability), with plain data in and plain data out that the game validates; the originals declare none and the tests prove they ask nobody ([`create/CONTENT.md`](create/CONTENT.md), "Rule hooks").

Read: what a skin author is given, [`create/SKIN_API.md`](create/SKIN_API.md); making one,
[`create/MAKING_CONTENT.md`](create/MAKING_CONTENT.md) Part C; the code, [`engine/SKINS.md`](engine/SKINS.md).

## Packs, the dev pack and the chain

All content comes in **packs**: a folder with a `pack.json`, or one `.larissa` pack file (a zip of that folder, read in place and read-only). The engine has no content of its own and no special
case for any pack: it plays one chosen pack and the packs it is laid over (`"base"`), looking everything up down that chain. A
pack in the project (`godot/packs/`) holds `.tres` files; a pack installed from anyone (`user://packs/`) holds only the data form (JSON, `.foe`, PNG, OGG), so installing one runs nothing. Two packs are
known by name: **`legacy`**, the original game built by the importer, and **`dev`**, committed placeholder content (shapes with
their names written on them, speech that says its own name) that is the folder `godot/packs/dev`, a dev installed in the user's folder, or the `dev.larissa` next to the game, is the fallback in a debug build when no other pack can be
played, is what an author copies to start a game of their own, and is what the engine's tests run on. Pack tools check, export,
install and copy packs from the editor, a terminal or the in-game pack screen. Lengths that hold up play (station trips, fades,
speech) are data a pack can override.

Read: [`create/CONTENT.md`](create/CONTENT.md), section 4; the code, [`engine/PACKS.md`](engine/PACKS.md); the dev pack and its
generator, [`tools/dev_pack/README.md`](../tools/dev_pack/README.md); what the engine still assumes about the original,
[`engine/HARD_CODED.md`](engine/HARD_CODED.md).

## Audio

Effects, speech and music play through one autoload by registry name. Music is MIDI rendered to OGG by the importer, or played
from the MIDI files through any SoundFont at runtime. A speech line lasts a number of ticks recorded in data, so playback never
changes how long a screen waits.

Read: [`engine/AUDIO.md`](engine/AUDIO.md).

## Tests

Two gdUnit4 suites: `godot/tests/engine/` tests the engine on the dev pack and needs nothing from the original; `godot/tests/legacy/`
checks the original game (fidelity hashes, whole Voyager and Expert runs) on the legacy pack and passes with a note when there is
none. The Python tools have their own pytest suite.

Read: [`engine/DEVELOPING.md`](engine/DEVELOPING.md).
