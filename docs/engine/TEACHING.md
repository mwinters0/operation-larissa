# Teaching guide: which Godot concept is shown where

Operation Larissa, a faithful Godot 4.7 port of *Operation Neptune*, is a complete game written as a model project. Every script
starts with a header comment, and most name the concept they teach (`## Teaches: ...`); this page is the index the other way round:
pick a Godot concept, find the files that show it. Paths are relative to `godot/`. Read [`ARCHITECTURE.md`](ARCHITECTURE.md) first
(scene flow, autoloads, data flow), then take the concepts in the order of the course. Tests are marked (T): they are small,
readable examples of how to check the same idea.

## Suggested order for a course

1. Scenes, nodes, the scene tree, the main scene. 2. Resources and data. 3. Input, signals, the game loop.
4. Physics and collisions. 5. Animation (`AnimatedSprite2D`, `AnimationPlayer`, `Tween`). 6. UI and Themes.
7. Autoloads and flow between scenes. 8. Audio. 9. Saving. 10. Testing. 11. Export.

## Where to look for "how did they know that?"

The game's behaviour was read from the original program with Ghidra; every number has a source. [`DESIGN.md`](../port/DESIGN.md)
tags facts V (verified in the binary), I (inferred) or R (recalled), and [`PORT_GAPS.md`](../port/PORT_GAPS.md) lists the known
differences between the port and the original. The decompilation tools are in `tools/analysis/ghidra/` (a headless PyGhidra
workflow, [`README.md`](../../tools/analysis/ghidra/README.md) there). A good exercise: pick a constant in
`data/*.tres`, find the decompiled routine it came from, and find the test that checks it. Then annotate the routine in the
Ghidra GUI (comments, variable names, types) and export your work so it can be committed and reviewed like code
([`GHIDRA_GUI.md`](../port/GHIDRA_GUI.md) sections 7 and 8).
